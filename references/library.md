# 模式 B：笔记库治理

## 最高边界

整合只能在同一一级章节内部进行。系统理论、运行规范、模拟机与训练、技术提示即使主题相同也不跨章合并。

| 情形 | 处理 |
|---|---|
| 同一一级章节内部真冗余 | 保留一处，删除其余 |
| 同章同一事实分散 | 归并到同节主位置 |
| 同章同一对象的不同角度 | 在同一节分小节综合 |
| 跨一级章节重复 | 各自保留，不移动、不归并 |
| 跨章节冲突 | 不修改任何一处，列入冲突清单 |

## 目标目录

```text
0 速查区          记忆项目 / 故障处置流程 / 关键限制值
1 系统理论
2 运行规范
3 模拟机与训练    原“机组训练手册”按主题并入本章
4 技术提示        未归类内容沉淀区
```

原“机组训练手册”按来源分类，维度与主题章节不一致，因此取消独立一级章。内容按主题进入第 3 章，并在 front matter 的 `source` 中标注 FCTM。

### 章内骨架

- 第 1 章：`组成 → 控制与操作 → 正常工作逻辑 → 保护与告警 → 失效表现`。“失效表现”只写现象与影响，不写处置。
- 第 2 章：`程序/导航 → 环境与运行条件 → 应急 → 人员与管理`。只放规则要求与限制值，执行流程放第 3 章。
- 第 3 章：`3.A 通用方法`、`3.B 正常科目`、`3.C 系统故障`、`3.D 特情处置`。

3.B 包含地面准备、中断起飞、离场、目视起落航线、目视盘旋和机动飞行。3.D 包含风切变、交通避让、烟雾着火异味、单发无指引和撤离。只有用户材料出现这些主题时才建立内容，不补写主题知识。

## 编号与机型标记

- 3.C 系统故障编号与第 1 章系统编号一一对应，例如 `1.6` 对应 `3.C.6`。
- 每个条目编号全局唯一。重号必须报告并提出重新编号方案，不能静默处理。
- 独立文档的 `A-1 / B-3` 编号并入库后作废，改用库编号；原块标题降为节内小标题。
- 每个条目带 `[NG]`、`[738]`、`[NG+738]` 或 `[待确认]`。原稿未明示机型时用 `[待确认]`，不得猜测。

## 阶段一：全局盘点

不修改任何内容，只输出：

1. 归类映射表：现有条目 → 新位置编号 → 依据；有争议的标“待定”。
2. 重复清单：位置对、重复类型、建议处理。
3. 冲突清单：位置对、差异点、需核对的原手册。
4. 待确认清单：机型未明、编号异常、表述含糊和可能缺失的主题。

输出后立即停止，等待用户明确确认映射表。不得把沉默当作确认。

## 阶段二：分批产出

映射表确认后按已授权范围连续分批输出正式内容，不新增逐批批准；新发现且影响归类的争议仅暂停受影响条目。每批说明处理了哪些重复、遇到哪些问题，并检查第 0 章同步义务。

## 第 0 章同步义务

第 0 章速查条目从第 1–3 章提炼，每条注明来源章节编号。修改第 1–3 章任何限制值、阈值或动作时，必须检查第 0 章有无对应条目并一并更新；交付说明必须报告是否触发同步。

## 增量维护

1. 用户把新知识点写入 `inbox.md`。
2. 用户提供 inbox 和相关章节文件，不要求无关章节。
3. 依据本次文件归类并输出更新章节。
4. 用户已要求修改本地文件并指定目标时，映射表确认后直接落盘和验证；未指定目标时使用任务输出副本，不覆盖不确定目标。Git 提交及外部同步按各自已有授权执行；未获授权时不执行，也不阻塞本地成果交付。
5. 需要完整笔记时再运行构建脚本生成 `.docx`。

Skill 不持有笔记状态。归类依赖未提供章节时必须要求补充，不得凭记忆归位。
