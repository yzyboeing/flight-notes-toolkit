# 给 AI 助手的操作指令：维护 737 理论知识笔记库

把本文件整段发给任何 AI 助手，它就能接手这个笔记库的整理、修改与同步。

---

## 〇、先判断你能做到哪一步

**第一件事：确认你有没有对本机的文件读写和 shell 执行能力。**

| 你有 | 你的角色 |
|---|---|
| 文件读写 + shell（Codex CLI、Claude Code、Cursor 等） | **完全模式**：整理 + 入库 + 构建 + 校验 + 提交推送，全程你做 |
| 只有对话（网页版 ChatGPT / Gemini 等） | **草稿模式**：只做整理，产出一个符合格式的 md 文本交给用户，由用户粘贴入库。**不要假装执行了命令。** |

不确定就先跑一条 `ls ~/flight-repos` 试试。跑不了就走草稿模式，并在开头告诉用户「我没有本机权限，只能给你源文件文本」。

**永远不要编造执行结果。**没跑就说没跑。

## 二、环境事实

```
~/flight-repos/
├── pub/           公开仓库 flight-notes-toolkit（方法论 + 工具链）
│   ├── prompt/SKILL.md          整理规则（真源）
│   └── tools/                   assemble.py  build_docx.js
│                                check_src.py  verify.py  sync.sh
└── gh-private/    私有仓库 flight-theory-notes ＝ Obsidian vault ← 笔记正文在这
    ├── sync.sh                  一键同步入口（包装，实际调 ../pub/tools/sync.sh）
    ├── notes_src/
    │   ├── 000 总目录.md         全库索引（id: MOC-ROOT）
    │   ├── MANIFEST.txt          对账清单
    │   └── 0…5 六个模块目录/      每个含一个 _XX 目录.md（MOC）与若干节
```

- **仓库就是 vault**，没有第二份拷贝，改文件即改仓库。

- 依赖已装好：`docx`（npm，在 gh-private/node_modules）、`pymupdf`（pip）、LibreOffice、`gh` CLI（已登录）。
- Obsidian Git 插件每 30 分钟自动 commit 一次本地快照（不推送）。你会在 `git log` 里看到 `chore: Obsidian 自动备份 …`，那是正常的，不要试图清理。

## 三、红线（违反了比不做还糟）

1. **笔记正文只进私有仓库。**内容派生自公司受控手册与 SOP。往 `pub/` 提交任何东西之前，跑一次泄漏扫描：
   ```bash
   grep -rnf ~/flight-repos/gh-private/.leakscan-keywords \
        --exclude-dir=.git ~/flight-repos/pub/
   ```
   关键词清单（公司名、机场四字码、基地城市、具体发动机型号、姓名、邮箱）放在私有库里，
   **清单本身也不能进公开库**——把这些词列出来等于直接公布了这份笔记涉及谁。
   有命中就停下报告，不要推。

2. **数值逐字保留。**不换算、不四舍五入、不「修正」看起来异常的值。DA/MDA、高度、速度、限制、频率、跑道数据发现可疑只标注不修改，交用户按现行手册裁定。被「自动纠正」错的数据比原始错误更危险，因为它看起来像被核实过。

3. **不基于臆测添加内容。**原始材料缺失就写 `【缺失，待原件补充】`，不猜写。

4. **技术冲突不自行裁决。**新旧内容打架时列出双方原文与所在章节，请用户定，不要自己选一个写死。

5. **`id` 不能乱改。**front matter 里的 `id` 决定全书组装顺序，改它会打乱整本书。文件名随便改（组装不读文件名）。

6. **推送前先看远端。**远端可能有本地没有的提交（用户在别的机器上改过）。先 `git fetch`，比对后再动，**不要用本地旧文件覆盖远端新内容**。README 这类两边都会改的文件最容易中招。

7. **不碰凭据。**不处理密码、token、登录流程。git 认证靠已配置的 `gh` CLI。

8. **删除要请示。**这个环境下删文件前先问用户，或改名备份代替删除。

## 四、流程 A：用户给了新材料

1. **读 SKILL.md**，按里面的结构方法整理成一节标准笔记（markdown + 内嵌 HTML 表格）。
2. **判定归属章节与编号**，按 SKILL.md 第一节的三条判据。跨不了判就列两个候选请用户裁定。编号顺延到该章末尾；要插在中间必须同时做全库交叉引用重映射并给出新旧对照表。**第四章顺序严格锁定，插入需用户明确许可。**
3. **写入** `notes_src/<模块目录>/<编号> <标题>.md`，front matter 写全 `id / title_cn / aircraft / source / related / updated`。
4. **更新索引**：该模块的 `_XX 目录.md`、`000 总目录.md`、`MANIFEST.txt`。
5. **跑同步**（见第六节）。
6. **交付**时附 SKILL.md 第三节要求的三份清单：已补充/修正（含依据）、存疑待证实、待用户裁定的安全关键项。

## 流程 B：用户要改现有内容

1. 先 `grep` 定位，确认要改的是哪一节的哪一处。
2. 改之前**检查全库有没有同一数值/动作/口令的其他出现**——主库大量交叉引用，改一处常常要改多处。漏改会造成前后矛盾。
3. 改完跑同步。
4. 报告改了哪些文件、哪些行，以及有没有连带影响别的章节。

## 五、写源文件的关键约定

完整规则看 SKILL.md 第六、七节，这里只列最容易踩的：

- `<em>` = 红色加粗，标阈值 / 限制 / 禁止性措辞 / 判据分岔点；`<strong>` = 黑色加粗，标关键术语 / 动作 / 结论。**一个单元格通常不超过一处红色，不整行整列标红。**
- 表格行类：`<tr class="hdr">` 表头 / `class="premise"` 共性前提通栏行 / `class="note"` 末尾补充通栏行。
- **同名标签不可自嵌**（`<em>` 里不能再有 `<em>`），`<em>` 与 `<strong>` 可互嵌。
- **正文笔记行首不许出现 `- * ▪ •`**——成品要复制进 OneNote，会被转成列表。层级用换行 + 加粗前缀标签表达。（MOC / 总目录用 markdown 列表是正常的。）
- 交叉引用写成 Obsidian 双链 `[[4.4 离场阶段航线规划]]`，组装时自动还原成「详见 4.4」。**正文里提到「双链」这个词本身时不要写成双链语法**，否则关系图谱里会挂空节点。
- 时间用缩写（3min，不写「3 分钟」）；检查单名用《》；机型差异用【】标在项目名后。

## 六、同步（完全模式）

```bash
cd ~/flight-repos/gh-private
./sync.sh "改了什么"          # 日常：只重建有改动的那一章，约 30 秒
./sync.sh --full "改了什么"   # 大改或改了渲染器：重建全书，约 1 分钟
./sync.sh --check             # 只校验，不构建不提交
./sync.sh --no-push "..."     # 构建并提交，不推送
```

它串起：源码校验 → 组装 → 渲染 docx → 转 PDF → 排版校验 → commit → push。**任一步失败即中止**，不会把有问题的内容推上去。

**两套校验互补，都要过：**

- `check_src.py` 查源头：front matter 缺失、`id` 重复、双链断链、HTML 标签开闭不配对、行首项目符号、MANIFEST 对账。
- `verify.py` 查排版结果：空白页、标签泄漏到成品、`▪ •` 残留、front matter 泄漏。

只跑一套会漏：源码干净不代表排版没问题，反过来也一样。

**提交说明前缀**：`add:` 新增小节 / `fix:` 修订内容 / `refactor:` 重排或改编号 / `docs:` 文档 / `style:` 排版与渲染器 / `rule:` 规则变更 / `chore:` 工具依赖。前四个推私有库，`style:` `rule:` 推公开库。

改完记得更新 `CHANGELOG.md`。

## 七、已知的坑

| 坑 | 表现 / 对策 |
|---|---|
| 字体决定页数 | 页数不能跨环境比较。缺中文字体的机器上同一份源文件曾编译出 534 页，装了苹方的 Mac 上是 370 页。报页数必须带字体条件。默认 PingFang SC / Helvetica Neue / Menlo，Windows 上用 `DOC_FONT_CN` 等环境变量覆盖 |
| git 转义中文路径 | 按路径匹配模块号要加 `-c core.quotepath=false`，否则拿到的是 `\346\250\241` |
| rowspan 列错位 | 算列宽和渲染单元格必须用同一套占位网格推真实起始列 |
| 嵌套标记被当字面文本 | `<strong>…<em>X</em></strong>` 需要递归解析，单层正则会把内层标签打印出来 |
| LibreOffice 与 Word 分页不同 | LO 用于自动化校验，最终以 Word 为准 |
| 两张表天生超一页 | 3.9 各类液压故障处置、5.6 GPS 干扰对各系统的影响，缩到 7pt 仍 550–600pt，只能自然分页。这是已知项，不是新 bug |
| docx 是生成物 | 永远不要直接编辑 docx，所有改动落在 `notes_src/` |

## 八、交付时怎么说话

- 先给结论，不写长篇后记。
- 报页数带上字体条件。
- 附三份清单（已补充/修正、存疑、待裁定）。
- 说明做了哪些结构调整：新增/移动/合并了哪些节、改了哪些编号。
- 提醒用户 docx 打开后按 `Cmd/Ctrl + A → F9` 刷新目录（TOC 是 Word 域，首次打开为空）。
- 不确定的地方直说不确定。**宁可多问一句，也不要让说不通的内容混进复习材料**——这是飞行复习资料，错误会带进座舱。
