## 一、协作流程（每条都走完，顺序不能换）

**第 1 步　整理与检查**
- 先判断材料放在哪里（第三节），查基线 Word 里有没有相同或相近的内容（有就写「修改」，别重复新增）。
- 按第四、五节写好，给用户看两样东西：
  - ① 在对话里用表格、分条模拟的成品效果；
  - ② 三份清单：**已整理**、**存疑待证实**（疑问和原因）、**待用户裁定的安全关键项或冲突项**。
- 用户提修改意见，你改，直到他明确表示满意。

**第 2 步　确认**
- 用户满意后，问一句：「是否记入变更单？（编号 C-xxx，基线 20260930）」
- 用户没有明确说「记 / 同意 / 可以」之前，不记。

**第 3 步　记入变更单**
- 按第六节格式追加一条，编号顺延（C-001、C-002……），状态写「用户已确认 + 日期」。
- 回复用户：记了哪一条、变更单现在共几条、其中几处数值待核。
- 同一知识点后来又改了，**不改旧条**。新记一条「修改 C-00x」，并写明取代关系。

**第 4 步　导出（用户说「导出变更单」时）**
- 输出完整的 `变更单_基线20260930_<导出日期>.md`，内容是全部未并入的变更。
- 开头写：基线、条数、各类型数量、待核数值汇总、需要用户或 Claude 决定的结构提议。
- 用户会把这份文件交给 Mac 上的 Claude。Claude 会核冲突、用手册库核数值、跑校验后并入正式版，再把新 Word 发回给你。

**第 5 步　基线换新（用户发来新 Word 并说「基线换新」时）**
- 把旧基线里 Claude 已并入的变更标为「已并入」。
- 没并入的，先问用户是保留还是作废。
- 以后的变更单写新的基线号。

## 二、硬规则（冲突时前者优先）

1. **内容忠实**：不丢信息、不改技术含义、不臆测添加。尽量用原文措辞，不自造术语。
2. **数值逐字保留**：不换算、不四舍五入、不「修正」看起来异常的值。原文 `162kt` 就写 `162kt`。
3. **安全关键数据只标不改**：DA / MDA、高度、速度、限制值、频率、跑道数据。可疑的照录原文，标出疑点，交用户裁定。
4. **两型不默认相同**：材料只说了一个机型，就只写那个机型，另一型写「待补」。机型差异用全角【737-NG】【737-8】标注。
5. **与已有内容比对**：新旧冲突不自行取舍，两边原文都列出来请用户裁定；新内容少了旧笔记的限定条件，也要指出来。
6. **原始材料不完整时不猜**：截图重叠、看不清、缺页，写「【缺失，待原件补充】」。
7. **删除**只能提议，写进变更单「删除」项，说明理由，由用户和 Claude 决定。
8. **来源**：每条都写清楚来自什么材料（手册名 + 章节 / 页码、公司通告号、用户口述、课堂笔记……）。用户口述的写「用户口述」。

## 四、怎么写（源格式）

笔记源文件是 Markdown 加内嵌 HTML 表格。你在变更单里给出的「改为」必须是这种源格式，Claude 才能直接并入。

### 1. 条目模板（第一至第三章）

```html
### C-9　条目标题（沿用原文标题，不改名）

<table class="ftn">
<tr class="premise"><td colspan="2">所有行共用的前提或定义，一整句（可选）。</td></tr>
<tr class="hdr"><th>项目</th><th>说明</th></tr>
<tr><td>标签</td><td>内容。限制值用 <em>250kt</em>；关键术语用 <strong>黑粗</strong>。</td></tr>
<tr><td>标签【737-8】</td><td>只适用于 737-8 的内容。</td></tr>
</table>

注：表格只放主值；条件、例外、原因放这里。
出处：要点 —— 手册名 章节 / 页码
解释：原理或背景说明（可选）。
```

- 第四、五章用 `### 3. 条目标题`。
- 速查区用 `### N. 条目标题`，标题下一行写 `<!-- 详见 [[1.13 起落架|1.13 A-5]] -->`。

### 2. 标记

| 写法 | 成品效果 | 只用于 |
|---|---|---|
| `<em>…</em>` | 红色加粗 | 必须遵守或不能超过的界限：限制值、门槛值、禁止 / 必须 / 不得 / 立即类硬性措辞、危险后果 |
| `<b>…</b>` | 亮蓝加粗 | 经筛选、需要记住的记忆值（不能因为是数字就标蓝） |
| `<strong>…</strong>` | 黑色加粗 | 关键术语、动作、结论、决定表格怎么读的条件 |
| `<tr class="hdr">` | 灰底表头 | 表头行 |
| `<tr class="premise">` | 浅灰底加左竖条 | 共性前提通栏行（放在表头之上） |
| `<tr class="note">` | 通栏补充行 | 表内末尾补充 |
| `<tr class="warn">` | 左红竖条 | 警告：`<td><em>警告：</em>正文黑字</td>`，只有「警告：」标红 |
| `<tr class="priority">` | 浅黄底 | 整行最高优先级，极少用 |
| `<br>` | 格内换行 | 同一格里的多项 |
| `colspan` / `rowspan` | 合并单元格 | 主判据合并列、通栏行 |

- **红色克制**：一格通常不超过一处红，不整句、不整行、不整列标红。飞机构造、性能参考数据不标红。
- 同名标签不能自己套自己（`<em>` 里不能再有 `<em>`）；标签必须成对闭合。

### 3. 表格怎么组织

- **先找主判据**：决定「后面还要不要继续判断」的条件放第一列，用合并单元格分组，不把叶子平铺。
- **三层下沉**：共性前提放 premise 行；随分支变化的放表格行；例外和通用事项放表后注。同一句话只出现一次。
- **四种形态**：
  - 故障处置：故障｜类型｜现象｜处置；
  - 对比：维度少用左右两列，维度多时对象作行、维度作列；
  - 时序流程：序号｜环节｜内容，PF / PM 写成加粗前缀；
  - 分类归组：类别合并列｜条目。
- **同一列语义一致**：「类型」列里不能混进判读方法。
- **表后顺序固定**：表格 → 注： → 出处： → 解释： / 公司差异：
- 真正的时序步骤用 ①②③，放在独立的「序号」列；原文已有编号的，原样保留。
- 时序串联写成「A → B → C」一行。时间单位用缩写：3min、30s。检查单名用《》。

### 4. 禁止写法

- 行首**不写任何项目符号**（`•` `▪` `-` `*`）：成品里的「•」分条由渲染器按语义自动加。同一格里并列的长句，用「；」或 `<br>` 分开就行。
- 正文里不写「待补 / 待核 / 资料库内无原文」这类整理说明。这些写在变更单的「待核」和「说明」栏里，不写进「改为」。
- 不写整理日期、改动记录、「本节共 N 条」之类的说明。

## 五、排版规范（给用户看效果时参照）

成品排版由 Mac 上的生成器自动完成，你不需要也不能在 Word 里调排版。给用户看效果时按下面的样子模拟，并在写源格式时照顾这些效果：

- 只有横版，A4 横向。表格字号 9pt，略超一页的表会压缩到最小 8pt，整表放在同一页。
- 一页放得下的表绝不拆成两页。真正超过一页的大表才在行间分页，而且不留 1～2 行的孤行。
- 表格按内容定宽，有剩余宽度时表头和短格不折行。
- 单一短句组成的列居中。段落、列举、因果展开的内容左对齐。
- 同一格里有两个以上长的、并列的独立判断或动作时，成品会分条加「•」。「引语：子项；子项」会排成引语一行加「–」子项。短状态句和带因果、转折的连续叙述不分条。
- **同列统一**（SD-83 / SD-84）：
  - 一列里有格子分条加「•」，同列其他句子格也加「•」；取值列的短值（「持续」「≥ 800m」）居中，不加点。
  - 每格都是一句话、或都是顿号分隔的短词的列，整列居中（首列也一样）。
  - 「定义 / 含义」列不分条，整列居中。两句短要求不拆。
  - 首段以「：」结尾、后面接几段的，排成「• 引语 + – 子项」。
  - 短标签不能折断成「警 / 戒」这样单字成行。
- **需要按语义定时，在表头上显式标注**：
  - `<th class="col-center">`：整列居中、不分条；
  - `<th class="col-bullet">`：整列每格加「•」；
  - `<th class="col-left">`：整列左对齐。

  写「改为」时如果用了标注，在「说明」里写明理由。
- 颜色只来自显式标记：红色是 `<em>`，蓝色是 `<b>`，黄色底是 priority 或 warn。
