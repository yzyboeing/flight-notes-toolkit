## 一、硬约束（任何情况下都不越线）

1. **数值逐字保留**：不换算单位、不四舍五入、不顺手取整。

3. **两型不默认相同**：涉及机型的数值两型都要查。
4. **依据只来自本机手册库**（第二节）：不上网、不用模型记忆补具体 B737 数值、限制或程序。
5. **用户提的问题先评估、定方案、问完再动手**（第七节第 1 条）；内容类大改动（改结构、改编号、删并内容、拆表、跨章迁移、删速查条目）先列清单给用户确认。
6. **不删文件**：要删的移到 `~/flight-repos/_to_delete/<日期>_说明/`；不对未加引号的变量跑 `rm`。
7. **推送**：日常重建只做本地提交（`sync.sh` 不推送）；出新基线时按第十节推送两库并打标签（标签在推送成功后再打）。公开工具库推送前必须过泄漏扫描（`push_all.sh` 自动）。
8. **同一时间只让一个 AI 写**：开工先 `git status`；发现别的会话正在改 `notes_src` 或 `pub/tools`，只做只读核对，先问用户。会真跑构建的测试放临时副本，不在正用的仓库跑。

10. **不改生成物**：`notes_src/**/*.md` 与 `速查/速查源.md` 是唯一内容真源；Word / PDF 由工具链生成。
11. **不处理密码、token 或登录流程**；OneNote 写入用已有授权的工具，只在用户指令时写。
12. **没跑就说没跑**：不编造执行结果；不能核实的写明原因。

## 四、内容写法要点（全文见《内容校对核心规则》）

### 机型
- **不标 ＝ 两型相同**。只适用一型：项目名后或句首加全角【737-NG】/【737-8】；同型各机号有差异写「部分机号：…」，不列具体机号。
- **两型共有的概念用左右对比表**（SD-170 / 194）：排法一「项目 ｜ 两型相同 ｜ 仅 737-NG ｜ 仅 737-8」，排法二「项目 ｜ 737-NG ｜ 737-8」（相同行跨两列合并）；对比表必须有「项目」列；不在格内混写。第 4 章程序步骤里的两型分支保留格内写法，登记《两型混写保留.json》。
- **能用表格把条款表达得更清楚的一律用表格**（SD-173）。

### 注与公司差异
| 写法 | 用在哪 | 规则 |
|---|---|---|
| 「注：标签——内容」 | 表后 / 段后 | 补充说明、学习性解释、条件说明；「解释：」一律改「注：」；一条目 ≤ 3 条（缩写注不计） |
| 「注：缩写——A：英文全称（中文）」 | 主场条目的第一张表 / 图之后 | 缩写注只放在以该缩写为重点的条目，每本一次（W06） |
| 「公司差异：标签——内容」 | 表后 | 只用于两份手册要求不同 |

- 表后顺序：表格 → 注： → 公司差异：。全书不写来源 / 出处（SD-138）。
- 不写进正文：事故经过、逐步算例（速查「例：」≤ 1 条）、带日期的整理记录、「待核」「手册未写」这类核对口吻。
- 原理类定义不写公式；随通告更新的名单不抄进笔记，只写查询位置。

### 符号
- 数值范围用「～」：两侧都是数字不留空格（2～3s），有单位或文字相邻两侧各留一空格（2450ft ～ 10ft）。
- 引号「」、嵌套『』；温度 ℃；时序步骤 ①②③，并列要点用圆点（渲染器加）。

## 五、颜色、表格与版式要点（判定以《排版规则总表》为准）

| 标记 | 成品 | 标什么 |
|---|---|---|
| `<em>…</em>` | 红色加粗 | 必须遵守或不能超过的界限：限制值、门槛、禁令、危险后果、决断时机；一格通常不超过一处红；约 25 字以上整句不标红 |
| `<b>…</b>` | 亮蓝加粗 | 要背的数值：系统参数、程序数值、门槛与时段 |
| `<strong>…</strong>` | 黑色加粗 | 关键条件、结论、标签 |
| `<td class="hl">` / `<tr class="warn">` | 浅黄底单格 / 警示通栏 | 特别注意的一两格 / 警示行 |

- 同一数值全书同色；改一处颜色要全书检索。
- **表格**：表头、首列居中加粗；取值与短语居中不加点；有长句（≥ 15 字）的列整列靠左加点（不论表头）；两列表第二列靠左加点（全是取值时居中）；序号表其余列靠左不加点；首列一律不加点；列宽以行数最少为纲；表格一律正文 9pt、可以跨页（续页重复表头，每截至少 1 行数据，页底不留孤表头 / 分组行、不拆合并格，SD-218），只有点名整页（`one-page`）的表整表同页。用户点名的列在表头显式标注（`col-center` / `col-bullet`），并登记《用户点名排版台账.json》。
- **插图**：不自行新增插图，用户点名才加；不收 FCOM 系统示意图；图注只写「图号　标题」；自绘图按 P05 标准（源码 `gh-private/figures_src/`）。
- **成品**：只出横版 A4；全书思源宋体（Medium / Bold），表内字号 ≥ 8pt；封面「版本号 <版本名>　·　YZYBOEING」；页脚「章名　节名 ｜ 第 X 页」，点击回主题目录；每节另起一页，每章 / 速查每段从新页开始；PDF 书签展开。

## 七、工作方式（用户定的固定做法，每条都要遵守）

1. **用户提问题的五步处理（2026-10-21 用户：「以后我每次讲完一处问题，先不要着急动工修改，首先评估合理性和必要性，以及你有没有更优的方案，然后定下方案再扫描目前的两个笔记找出所有相关需要优化的地方定下最终方案再询问我还有没有其他问题，等我最终说没有可以开始优化再执行优化」）**：
   ① 评估合理性与必要性 → ② 有更优方案就提出 → ③ 定方案 → ④ 扫两本找出全部相关处、定最终方案 → ⑤ 问「还有没有其他问题」。每条记进工作区当期《优化意见记录_<基线>.md》（原话、位置、核实、方案、同类扫描、影响范围、状态、验收）。期间**不改源文件、不重建**；用户说「没有，可以开始优化」后一次执行、一次收口。规则方案本身也照此办理（「先别动」= 不改任何文件）。
2. **请用户拍板前先把方案正文发出来**，提问只放决定本身；有更好的做法先说，用户同意就照建议做。
3. **提方案时先预判副作用**（窄表、长句、跨页、两本同表等极端情况），需要时先出单节样张。
4. **用户给的规则按原话执行**，不自加阈值和例外；用户定的排版规则，检查器报**错误**，例外不能悄悄推翻。
5. **改全书规则前先看影响面**（排版规则总表 G3）：列出两本所有受影响的表 / 列，出 2～3 页样张，和方案一起给用户定。
6. **精简 / 改写前列全原文要素**（数值、条件、例外、机型），改后逐项核对，附无损声明（教训：高度表 75ft 漏掉）。
7. **新增知识点先通查已有内容**（第八A节）；**补入只逐行合并、不整表替换**；**删速查条目须用户确认**。
8. **用户说过的排版要求变成永久检查**：登记《用户点名排版台账.json》，每次重建自动实测；执行完每条意见要验收（第八节第 9 步）。
9. **排版问题调两轮不收敛就停**：个别孤字、略多一行接受并记一句；影响阅读的给 2～3 个做法与代价、标出推荐，用户定了再动。
10. **交付按需**：全书 PDF / Word、OneNote 只在用户要求时给；用户说「最新文件」只给速查 PDF；完整版和 Word 点名才给。
11. **交接走谷歌云盘**（`~/Library/CloudStorage/GoogleDrive-yzyboeing@gmail.com/My Drive/03_AI协作交接/`，桌面 `Muse交接包`、`噜噜收件箱*` 是它的链接）：写完等上传确认再通知；复制后 md5 对不算数，上传后按 DriveFS 数据库逐个比对大小（第十节）。

## 八、标准工作流程（执行阶段）

```
开工检查 → 修改源文件 → 两本联动 → 源头校验 → 单节预览 → 全量重建 → 收口到错误 0 → 看成品页 → 逐条验收 → 本地提交 → 出基线（按需）→ 交接记录
```

1. **开工检查**：读《现状一页纸》和《00_先读我》最新一轮；`cd ~/flight-repos/gh-private && git status`；`ps aux | grep -E "sync.sh|soffice"` 确认没有别的构建在跑。
2. **修改源文件**：内容改 `notes_src` / `速查/速查源.md`；排版问题改生成器 `pub/tools/build_docx.js`（一处改全书生效，不手调单页）；新排版要求同时加进 `check_layout.py`（或 `check_struct.py`）和《排版规则总表》。
3. **两本联动（SD-109）**：检索两本同一数值、术语、缩写、知识点，相关位置一起改；增删条目用 `move_items.py`；改共有表两本同改。
4. **源头校验**：`python3 ../pub/tools/check_src.py --src notes_src`、`check_blocks.py`、`check_struct.py` 全部通过。
5. **单节预览**：`python3 ../pub/tools/preview.py <节号…>`（每节 1～2 分钟），改到 0 错误再全量。
6. **全量重建**：`DOC_EDITION=<版本名> ./sync.sh --full "改了什么"`（有意删除速查表行时前面加 `SRC_NO_S7=1`；约 17 分钟；生成两本、跑全部检查、本地提交）。
7. **收口**：读 `build/排版检查报告.md`——**错误必须为 0**。T13 / T14（列空白 / 该加宽）收不拢的表，跑 `python3 ../pub/tools/closeout.py --repo .`（先看列单，再加 `--apply`）：按实测在源文件表头写 `w-NN` + `w-lock`，并清掉 `build/keep_force_*.txt` 里该表的旧 W / NW / BW / F / C 记录；孤标题页可加 `P:标题` 记录。新建议逐条看成品页，裁定写进 `排版建议裁定.json`。
8. **看成品页**：`pdftoppm -f N -l N -r 60 -png <pdf> out` 渲染被改动的页和用户点名的页目视检查；插图页用 `figaudit.py <pdf> <输出目录>` 拼版过目。没看过成品不能说「已验证」。
9. **逐条验收**：优化意见记录每条填「验收」（机判的看 K-USERPIN / 检查报告，人工的写成品页码）。
10. **记录**：见第七节第 14 条；新规则写进三份现行规则（排版 → 总表，内容 → 核心规则，流程 → 本文），来历编 SD 号写进《长期决策》。

**排障经验**：
- 与改动无关的孤页或坏断点，先查 `build/keep_force_*.txt` 里有没有过期的 `P:` 记录（点名整页表还看 `~N` / `!`），删掉那一行再重建；整表下移 `B:` 与大表拆开 `SB:` 记录只在本次运行内有效，不用清。
- 「LibreOffice 没能生成 PDF」且无报错，多半是两个构建抢同一个配置目录，确认只有一个构建在跑。全量重建时速查版与完整版并行（速查用独立配置 `lo-sync-profile-qr`，日志 `build/quickref_run.log`）；要排查时加 `SYNC_SERIAL=1` 改回串行。
- fit_fix 在两种列宽状态间来回跳（trace 里 `two-state`）时，同样的源文件两次重建个别格的列宽会差几 pt，可能让一条孤字在「建议」和「错误」之间来回——属已知问题，待提速轮 E4 / E5 解决；遇到时按错误处理（借宽或 `closeout.py` 锁宽）。
- 改生成器后先 `node --check build_docx.js`；改 docx XML 的正则不要跨越 `<w:r>`。
- 图表并排的外层表紧挨另一张表时 LibreOffice 会把两张表并成一张——生成器已在前后加隔断段，不要删。

**没有工具链（只能对话）时**：按第八A节产出知识点卡和源格式文本，由用户或 Mac 上的 Claude 入库；手工报出：条目集合前后相等、原文逐行都在、每个数值能回查、标签配对；**明确列出无法验证的项目**。

## 十三、踩过的坑（不要重犯）

| 边说边改、每处问题都全量重建 | 一轮 8～12 次重建、2.5～3.5 小时 | 第七节第 1 条五步处理，一轮执行一次 |
